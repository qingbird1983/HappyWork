# ADR-0013：Phase 3 Hook 只允许编译期内置，暂停签名/TOFU

- 状态：定稿（2026-10-30，随 Phase 3 立项放行）
- 日期：2026-10-30
- 关联：[architecture/04](../architecture/04-security-and-hooks.md) §Hook 系统/风险与待决；[ADR-0005](ADR-0005-mvp-security-downgrade.md)；Phase 3 范围合同

## 背景

architecture/04 把"进程内 Go Hook"定为 MVP 唯一形态，同时留下待决：Hook 签名密钥签发（倾向本地生成 + 首次加载 TOFU 指纹展示）。若没有动态代码加载，签名对象并不存在；若引入动态加载，则同用户进程可篡改配置与密钥，TOFU 只能防"意外变更"，防不了同权限攻击者。

## 决策

1. Phase 3 的 Hook **只能是编译进二进制的 Go 实现**：内置 Hook 注册表，配置只能按名字选择/参数化，不能加载任意代码、脚本或插件。
2. **不实现签名与 TOFU 密钥**。启动时计算已加载 Hook 配置的 SHA-256 指纹写入日志（`hooks fingerprint`），供跨会话比对；界面上不宣称"已签名/可信"。
3. 配置 `hooks.d/*.yaml` 严格 schema：未知 Hook 名、未知字段、非法参数一律拒绝整份配置；Hook 系统整体禁用并在 AppInfo 告警，应用仍可启动。
4. after 类 Hook 只读：不得修改参数或结果；before_tool 的改参仅限工具声明的白名单字段，并逐次写审计。
5. 外部进程 Hook / 动态 Hook / 自定义工具注入不属于 Phase 3；将来立项须独立 ADR，先解决进程隔离、资源限制、签名与供应链，再谈信任。

## 理由

- 签名解决的是"这段代码/配置是否来自可信发布者"；当加载面不存在时，签名只是安全剧场。
- 编译期 Hook 的攻击面等于主程序本身，同用户威胁模型下 TOFU 无法提供实质保障；把复杂度留给真正需要隔离的外部形态。
- 严格配置 + 白名单改参 + 失败策略，已能覆盖 Phase 3 的扩展与审计需求。

## 后果

- 积极：无动态代码执行面；不引入密钥生命周期与 UI 信任话术；实现与测试范围可控。
- 代价：第三方无法在 Phase 3 注入 Hook；配置仅能启用内置能力。
- 重新评估条件：计划支持外部进程 Hook、WASM/插件或自定义工具分发时——需独立 ADR，定义签名、隔离与吊销。
